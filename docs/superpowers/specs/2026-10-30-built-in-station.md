## 1. Summary

The shared design is approved as the target architecture. Agora.Build is the control plane (accounts, sign-in,
credentials, integration management, Stoa, the voice assistant pipeline). Station is the data plane (encrypted
storage, R9 relay, the agent runtime, the assistant's LLM with its context and tools). Signing in never grants
device authority.

Before Phase 1, Auth had user sign-in, refresh rotation and signed access tokens for resources in a static clients
file, but no client credentials, `private_key_jwt`, token exchange, runtime clients or registered Stations. **Phase 1
is built and merged (2026-10-25/26)** and its live dev tests are done (2026-10-30, §6); this design now continues with
the built-in Station (§3.3.2, D24) and built-in apps (§3.3.3, D25).

## 3. Design

### 3.1 Integration credentials: each integration is an Auth client

When a person creates an integration (Discord, Custom App / API, or the assistant), Portal asks Auth to create a
**client** for it:

- `client_id` = the integration ID; the owner is the person's `ab…` account;
- client authentication is **`private_key_jwt`** (RFC 7523): the integration signs a short assertion with its own
  private key, and Auth checks it against the integration's registered **public** key;
- allowed resource: exactly the Station the person selected; allowed scopes: the operations they selected.

**Who generates the key.** Whoever runs the integration, never Agora.Build:

| Integration | Key pair generated by | What Agora.Build stores |
|---|---|---|
| Custom App / API | The developer (any JOSE library), or Portal **in the browser** with WebCrypto on request: the private key is downloaded and never sent to the server | The public key (JWK) |
| Discord, assistant | The Station agent module or Agora.Build service that runs it, in its own protected storage | The public key |

Only public keys reach Auth, so a leaked Auth or Portal database reveals no integration secret.

The integration gets access tokens with the **client-credentials grant**:

```http
POST https://auth.agora.build/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=<integration id>
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=<JWT signed with the integration's private key: iss=sub=client_id, aud=token endpoint, jti, exp ≤ 60 s>
&resource=https://station.example
&scope=agent.view agent.prompt
```

The token is the format Portal already verifies (`at+jwt`, ES256), with:

| Claim | Value |
|---|---|
| `iss` | `https://auth.agora.build` |
| `aud` | the selected Station's origin |
| `sub` | the integration owner's account (`ab…`) |
| `client_id` | the integration ID |
| `scope` | the granted operations |
| `r9_svc` | SHA-256 fingerprint of the integration's R9 service public key (§3.1.1) |
| `exp` | **5 minutes** after issue |

Station verifies tokens **locally** against Auth's public keys (JWKS): no Auth call per request, refetch on an
unknown key ID.

This settles the shared design's "service-to-account delegation" gap (its lines 339–346): Auth attests the binding
by issuing a token whose `sub` is the owner and whose client is the integration. No human session is impersonated,
no refresh token is copied, and Station never maps a service subject to a person by email.

#### 3.1.1 Binding the token to the R9 service identity

Portal records the integration's R9 service public key when the native manager approves it (§3.6), and Auth puts
its fingerprint in every token as `r9_svc`. Station refuses a token whose `r9_svc` doesn't match the service
identity it holds for that integration. The token is still **not** R9 authority: the agent module acts through its
own R9 service identity, which a native manager signed, and every request is limited by the token's scopes, the
integration's policy in Station and the host-verified R9 grant (shared design, lines 368–373).

#### 3.1.2 Quotas

Each integration has a configurable rate limit, **default 200 requests per second**, applied by Auth on the token
endpoint and by Station on its API. Portal shows and edits it per integration; Agora.Build sets the maximum.

### 3.2 Revocation, rotation and outages

| Event | Behaviour |
|---|---|
| Revoke an integration | Auth disables the client: no new tokens. Existing tokens work until they expire, **at most 5 minutes**. Portal also pushes the revocation to Station, and Station polls (§3.5). R9 removal is a separate step signed by a native manager. |
| Rotate the key | The owner registers a new public key. Auth accepts assertions signed by **both** keys for a **10-minute overlap**, then drops the old one. (Auth keeps a small list of keys per client, so the overlap is cheap to build.) The R9 service key is unchanged. |
| Auth unavailable | Issued tokens keep working until they expire; new tokens can't be issued, so integrations stop within 5 minutes. |
| Auth rotates signing keys | Station refetches JWKS on an unknown key ID, at most every 5 seconds per key ID, and trusts cached keys for at most 1 hour during an outage (Portal's current rule). |

### 3.3 Registered Stations (custom relays)

Every Station, including a self-hosted custom relay, is registered with Agora.Build:

1. Any signed-in account can register one. In Portal, **Stations > Add Station**, enter its origin
   (e.g. `https://station.example`).
2. **Proof of control:** Portal generates a value; the Station serves it at `/.well-known/agora-build-station`;
   Portal checks it over HTTPS, then asks Auth to register the Station.
3. Auth stores it in a **registered-Stations table** (not the static clients file): origin, owner account, status,
   created and last-verified times, and the accounts allowed to use it.
4. **Default: only the registering account can use it.** Nobody else can sign in to it, relay through it or create
   integrations on it.
5. **Sharing (§3.3.1)** is done from Portal by the owner.

**Making sign-in work with a custom relay.** Registering a Station makes everything that works with
`station.agora.build` work with it:

- Auth registers the Station's origin as a resource with the same scopes as `station.agora.build`
  (`astation.remote` for native clients, the integration scopes, `station.read` for the browser), so Astation and
  integrations get tokens whose `aud` is that Station;
- Auth creates the Station's own client for reporting to Portal (§3.5);
- Astation and Atem point at it with the same settings they use for `station.agora.build`
  (Atem's `astation_relay_url`); nothing else changes in the client;
- the Station checks every token's `aud` equals its own origin and that `sub` is an allowed account.

`https://station.agora.build` is the **built-in Station** (§3.3.2): a full Station on the same protocol, admitted by configuration instead of proof of control.

**Shared/public relays** (a Station serving people who aren't the owner's invitees): **later** (owner decision).

#### 3.3.1 Sharing a Station

From **Stations > <Station> > Share**, the owner adds other Agora.Build accounts. Auth adds them to the Station's
allowed accounts; each of them can then configure that Station as their relay in their own Astation (the same
setting as `station.agora.build`). Removing someone stops new tokens for them at once; their existing tokens
expire within their lifetime. Sharing grants only use of the relay and Station services under each person's own
account: accounts stay separate (shared design, lines 141–147).

#### 3.3.2 The built-in Station (`station.agora.build`)

**Owner decision (2026-10-30, D24); for review by Astation and Atem.** The built-in Station and custom Stations are
the same kind of thing. They share one protocol with Auth, Portal and Atem. A custom Station may add functions its owner
wants; the built-in Station may add functions Agora.Build wants; both keep the shared protocol. What differs is only how
a Station is admitted and who may use it.

**1. The shared Station protocol** (every Station implements it; nothing in it depends on the kind of Station):

| Direction | Contract |
|---|---|
| Native apps → Station | `astation.remote` token from Auth with `resource` = the Station's exact origin; `aud` = origin, `sub` = the person (`docs/station-tokens.md`, rules A1–A9) |
| Integrations → Station | `i-…` client, `private_key_jwt` + client credentials, `aud` = origin, `sub` = integration owner, `r9_svc`, ≤ 300 s; no token before native approval |
| Station → Portal | Report client `s-…` (`private_key_jwt`, `station.report`, resource = Portal origin): `POST /api/v1/stations/reports`, `GET /api/v1/stations/changes?cursor=` with `ownerAccount` in snapshots and `409 cursor_ahead` recovery |
| Portal → Station | Unsigned push hint `POST <origin>/agora-build/v1/changes {cursor}` (poll only, no authority) |
| Browser → Station | 5-minute `station.read` token by token exchange; `GET <origin>/agora-build/v1/details`, CORS from the Portal origin only |
| Station ↔ Atem/Astation | R9 relay and service membership as in the shared design; native approval binds `r9_svc` |

**2. What differs:**

| | Built-in Station | Custom Station |
|---|---|---|
| Admission | **Configured** in Auth's settings by Agora.Build; no proof of control | Registered in Portal with proof of control (§3.3) |
| Report key | Configured by the operator (public JWK only; the private key stays on the Station) | Given at registration |
| Who may use it | **Every signed-in account** that is not disabled (access mode `any_account`) | The owner and the accounts it is shared with (access mode `members`) |
| Owner | **No user owns it.** It belongs to Agora.Build, administered by Agora.Build admin accounts (configured, the same accounts as the Portal's `PLATFORM_ADMINS`). **Nobody can unregister it** through any API or page, admins included; only Agora.Build's configuration and a deploy can change it | The registering account; it can remove the Station |
| Integrations | **Only once Agora.Build supports hosted execution there** (like Station AI): then any account may create them on it, each owned by its creator; until then creating one is refused. Active integrations per account by plan (owner decision): **Basic 4, Premium 10, Principal and Fellow no cap** | The owner and members; **no cap on any plan** |
| Station-owner actions on others' integrations (pause, revoke) | Agora.Build admin accounts | The Station's owner |
| Default | **Every account's default Station.** Always available; a person can switch back to it at any time | Optional; a person chooses it in Astation |
| Extra functions | Agora.Build's choice, including Station AI once it supports it (D21 revised) | The owner's choice, on the same protocol |

**3. Configuration.** Auth's clients file gets a `stations` list; the static `station.agora.build` resource is removed
from `resources` (Auth refuses to start if an origin appears in both):

```json
"stations": [
  { "origin": "https://station.agora.build", "name": "Agora Station", "access": "any_account", "integrations": false,
    "admins": ["ab<Agora.Build admin account>"],
    "reportKey": { "kty": "EC", "crv": "P-256", "alg": "ES256", "x": "…", "y": "…" } }
]
```

`origin` follows the same rules as registered Stations (https, no path); `reportKey` is a public JWK (a private member
is refused); `integrations` (default `false` for a built-in Station) says whether integrations may be created on it;
`admins` lists existing Agora.Build admin accounts (the Portal's `PLATFORM_ADMINS`), at least one. There is no owner. Dev uses its own built-in Station at **`https://station-dev.agora.build`** (owner decision), never the production
origin.

**4. Auth.**
- **Seeding.** At startup, under an advisory lock, Auth upserts each configured Station as a registered Station row
  flagged `built_in` with its `access` mode and creates its report client `s-…` once (kept by origin across restarts).
  A changed `reportKey` is added as a new key with the usual 10-minute overlap, then the old key is dropped. **A seeded
  built-in Station missing from the file makes Auth refuse to start** (nothing is revoked); retiring one needs an
  explicit entry with `"retired": true`, which revokes its report client and integrations as for a removed Station
  (2026-10-30 ruling: an accidental edit must never revoke every integration on the shared Station).
- **Access modes.** Every place that asks "may this account use this Station" (native Station tokens, integration
  creation, the final token gate, token exchange for `station.read`) checks: `members` → owner or member;
  `any_account` → any account that is not disabled.
- **Admins.** On a built-in Station the configured admins hold the Station-owner rights (pausing or revoking other
  people's integrations on it, listing its integrations). They are not its owner and cannot remove it.
- **Management API.** `GET /manage/v1/stations?account=` also lists built-in Stations, with `builtIn: true` and the
  `access` mode. Removing a built-in Station or adding/removing its members answers `409 built_in`; registering its
  origin answers `409 origin_taken`. No API removes it, whoever asks; dropping it from the configuration is the only way. Integration creation on it answers `409 not_supported` while
  its `integrations` setting is `false`; when `true`, any account may create one (the actor must equal the owner of the
  new integration, as now).
- **Static resource retired.** `station.agora.build` goes through the registered-Station code paths; the special case
  for static Station resources is removed once no clients file uses it.

**5. Portal.**
- The Stations list shows the built-in Station for every signed-in account, marked "Built in", with Details and
  without Remove or Share; registering its origin is refused. Agora.Build admins see admin controls for its integrations
  (pause, revoke); nobody sees Remove.
- Integrations: the Station selector offers the built-in Station only while integrations are enabled on it (Auth's
  `integrations` setting, reported in its Station listing); then creation, approval, pause, resume, revoke, renew, quota
  and keys work as for any Station, and Agora.Build admins hold its Station-owner rights.
- **Plan limits on the built-in Station.** Before asking Auth to create an integration on a built-in Station, Portal
  counts the account's active integrations there (every state except `revoked`, and not expired) and refuses at the
  plan's limit: **Basic 4, Premium 10, Principal and Fellow no cap**, with `403`, code
  `plan_limit`, and the message "Your plan allows N integrations on the built-in Station. Revoke one, upgrade, or use
  your own Station." Custom Stations have no cap on any plan. The plan is Portal's (the same plans as membership and
  billing); Auth does not know plans and does not count. If an account moves to a plan with a lower limit, its existing
  integrations keep working until they are revoked or expire; new ones are refused until it is under the limit.
- The change feed and reports for the built-in Station work as for any Station: its report client sees every
  integration on it (each with `ownerAccount`), and only those. Push hints go to its origin.
- Reconcile treats `builtIn` Stations as present for every account and never revokes integrations because a
  built-in Station is "missing" from one account's list.

**6. Station (`station.agora.build`, Astation's server).** Generates its report key pair (the private key stays on the
Station) and hands Agora.Build the public JWK and its RFC 7638 thumbprint; runs the same report/feed client as a
custom Station (no proof-of-control endpoint needed); serves `/agora-build/v1/details` with `station.read` and CORS
from the Portal origin. Station AI (MCP, LLM, Agent) may be offered once it is supported (D21 revised); until then it
refuses those requests with a clear "not available on this Station yet" message.

**7. Choosing a Station (Astation, Atem).** The built-in Station is every account's default relay. A person who adds a
custom Station may switch Astation and Atem to it, and may switch back to the built-in Station at any time; the
built-in Station is always there to return to. Switching relays repeats the Atem/Astation verification for the new
relay (the trust and pairing checks Astation and Atem already run for a relay change); Auth and Portal are not
involved beyond issuing `astation.remote` for the chosen origin. Otherwise Atem does not change: the built-in relay
keeps its origin and `astation.remote`.

**8. Security.**
- Agora.Build admins administer the built-in Station but do not own other people's integrations on it: they can pause
  or revoke them (Station-owner rights), never approve them or act as their owner.
- Every integration still needs its owner's native approval; `any_account` opens use of the Station, not anyone's
  agents.
- The built-in Station's operator sees the `ownerAccount` of integrations hosted on it, as any Station operator does.
- Load on the shared Station: the plan limits above, each integration's token quota and the Portal's per-account rate
  limits.
- Enabling integrations or Station AI on the built-in Station means Agora.Build's server processes the agent content
  of the accounts that use them there; Astation tells the person so when they approve such an integration or turn
  Station AI on there.

**9. Migration and rollout** (after the Phase 1 live tests):
1. Station: generate the report key pair; send the public JWK and thumbprint.
2. Auth: release seeding and access modes; add the `stations` entry and remove the static resource in the dev clients
   file; verify `astation.remote` tokens for the same origin still verify at the Station (tokens issued under the
   static resource expire within 15 minutes).
3. Portal: release the built-in listing; verify on dev with two accounts (creation, approval, reports, feed,
   details, refusal of remove/share/re-register).
4. Production: the same, with the production origin and keys, on the owner's approval.

**10. Tests.** Seeding is idempotent across restarts and Auth instances; key rotation overlap; removal revokes;
`any_account` allows any non-disabled account and refuses a disabled one; `members` unchanged; `409 built_in` and
`origin_taken`; `409 not_supported` for integration creation while disabled; plan limits on the built-in Station (Basic 4, Premium 10,
Principal/Fellow none; revoked and expired ones not counted; custom Stations never capped; a downgrade keeps existing

breaking `astation.remote`; Portal listing, refused actions

#### 3.3.3 Built-in apps (Portal, Astation, a mobile app)

**Owner direction (2026-10-30, D25).** Agora.Build's own apps (the Portal, Astation, and a planned **built-in mobile
app**) are first-party clients of Auth. People sign in to them as themselves. They are not integrations (a person's own
apps or bots acting on their agents, created at runtime and natively approved) and not Stations.

| | Added how | Signs in as |
|---|---|---|
| Built-in apps | **Once**, in Auth's clients file (a new kind of app is the one-time configuration change) | The person (authorization code + PKCE, or device code) |
| Integrations | At runtime in Portal, each natively approved | Its own `i-…` client, acting for its owner |
| Stations | Built-in by configuration; custom through Portal | Its own `s-…` report client |

**The mobile app** is a native client, e.g. `agora-mobile`: public (no secret), PKCE required, refresh tokens with
rotation, first-party (no consent page). It requests only what it uses:

- `astation.remote` on the person's chosen Station (built-in or custom, exact origin), to view and control their agents
  remotely through the shared Station protocol; no per-Station configuration;
- `integrations:read` (and `integrations:approve` only if Q5 allows approving on the phone) on the Portal resource.

**Auth change needed: mobile redirect URIs.** Auth accepts only `http://127.0.0.1/callback` for native apps today,
which works for desktop apps (Astation, Atem) and not on a phone. Add the RFC 8252 forms for native clients:

- a **claimed https redirect** (preferred), e.g. `https://agora.build/app/callback`, served with Apple associated
  domains and Android app links so only the app can receive it;
- or a **private-use reverse-domain scheme**, e.g. `build.agora.mobile:/callback` (RFC 8252 §7.1), registered exactly.

Both are matched exactly like other redirect URIs, PKCE S256 stays mandatory, and device code remains a fallback. The
clients-file validation accepts these forms only for `type: "native"` clients.

**Push notifications** (an approval waiting, an agent asking a question) are later work: they need a push service and
device tokens, owned with Astation's mobile work.

Open: Q5 (approving integrations on the phone).

### 3.4 Native access to a Station

- `astation.remote` for the native `astation` client on the built-in Station and on each registered Station (§3.3).
  Phase 1 did it with a static `https://station.agora.build` resource; D24 replaces that with a configured built-in
  Station (`https://station-dev.agora.build` on dev), keeping the same native contract.
- Add `auth_time` to access tokens, so Station can require a fresh sign-in (`max_age=0`) for sensitive steps.
  `auth_time` reflects the last real sign-in; refreshing a token does not change it.
- A Portal token can never authorize a Station resource: different audience, and Station checks it.

### 3.5 Station and Portal talking to each other

| Direction | How |
|---|---|
| Station reports to Portal (integration became Ready, host accepted, errors) | The Station's own Auth client (`private_key_jwt`, client-credentials) with scope `station.report` on the Portal resource; the token's `client_id` identifies the registered Station, and Portal accepts reports only for integrations on that Station |
| Portal tells Station about revocations, pauses and policy changes | **Both push and poll.** Portal pushes a signed change notice to the Station right away; Station also polls Portal every minute for changes since its last cursor, so a missed push is caught. The token lifetime (5 minutes) bounds the worst case either way. |
| The browser reads private details from Station (labels, runtime status) | Portal asks Auth for a **token exchange** (RFC 8693): the signed-in person's session is exchanged for a 5-minute token with `aud` = that Station, scope `station.read`. Portal hands it to the browser, which calls Station directly (Station allows CORS from the Portal origin). Portal never sees the response. |

### 3.6 Portal: Account > Integrations

| Surface | Callers | Purpose |
|---|---|---|
| `/account/integrations/` | The website | List, create, configure, rotate, pause, revoke integrations |
| `/account/stations/` | The website | Register, verify, share and remove Stations |
| `/api/integrations/...`, `/api/stations/...` | The website (cookie) | The same operations |
| `/api/v1/integrations/...` | Native apps (access token) | Astation lists pending approvals and reports a signed approval; scopes `integrations:read`, `integrations:approve` |

**Pending approvals:** Portal keeps the **metadata** (integration, Station, requested operations, expiry, state,
who must approve); the **exact request body** a native manager signs lives on the Station. Astation fetches the
body from the Station, shows it, has the manager sign, and publishes through the shared core; Station reports the
result to Portal.

States follow the shared design: Awaiting approval, Provisioning, Waiting for host, Ready, Paused, Expired,
Revoking, Revoked. **Portal never sets Ready itself**; only an authenticated Station report does.

Expiry: default **30 days**, maximum **90 days** (the R9 service contract).

**Retention: kept forever, in each owner's database (D19).** Integration metadata, the agent module's operational
state and receipts are kept indefinitely, in plain append-only PostgreSQL tables, not in the R9 log:

| Data | Database | Notes |
|---|---|---|
| Integrations, Stations, sharing, pending-approval metadata, state changes | **Portal's PostgreSQL** (the existing database, covered by the HA/Patroni setup) | Rows are never deleted; revoking sets a status. Every state change is appended to an `integration_events` table with time, actor and reason. |
| Integration clients, public keys, registered Stations, allowed accounts, audit | **Auth's PostgreSQL** (next to `oidc_payloads` and the audit tables) | Access tokens (integration and assistant session tokens) are **not** kept; they expire and are cleaned up as now. Kept forever: issuance audit rows (client, `sub`, Station, time) and key history (retired public keys marked, not deleted). |
| Agent module operational state and receipts | **Station's PostgreSQL** (the Station server already runs PostgreSQL and Redis) | Receipts that reference private content stay encrypted. Redis holds only short-lived routing state, never history. Schema and encryption are the Station owner's design. |
| Assistant conversation history | **Portal's PostgreSQL** | Kept on Agora.Build (D8). By plan (owner decision): **free (Basic) accounts 90 days, paid (Premium) accounts forever**. A daily job deletes free accounts' conversations older than 90 days. When a paid plan ends, conversations older than 90 days are kept **30 more days**; the person is warned when the plan ends and again a week before, then they are deleted unless the person upgrades again (owner decision). |
| R9 signed membership log | Not a database: Atem's signed log (at most 1,024 entries, 256 members; shared design lines 683–686) | Station archives each signed entry into its PostgreSQL when it is published, as an **availability backup, never a source of trust** (entries are signed). **No compaction in R9** (D23, Atem owner): capacity isn't urgent (one entry per renewal or removal, about 40 a year for 10 integrations on 90-day renewals). Instead, a renewal rate limit and a clear "device list nearly full" warning. Checkpoints are a possible future revision (a new anchor confirmed in an owner ceremony with a safety code), only if a real account nears the cap. |

What "forever" requires:

- **Append-only:** status columns and event tables; no `DELETE` in normal operation.
- **Growth:** event and receipt tables partitioned by month, so recent queries stay fast and old months stay cheap.
- **Backups:** Portal and Auth use their existing PostgreSQL backups (`pg_dump`, Patroni); Station needs its own.
- **Export:** a per-account JSON export of integrations, events and receipts from Portal and Station.
- **Account deletion is the one exception (owner decision): all of the account's data is permanently deleted
  14 days after the person deletes the account.**
  - **At once:** the account is disabled: signing in leads only to a restore page (below), and no app or token
    can use it; every integration is revoked and its client disabled (no new tokens; issued
    ones expire within their lifetime); assistant sessions end; the person's registered Stations are unregistered
    and their sharing removed; the account is removed from other people's shared Stations; Portal pushes the
    revocations to the affected Stations as usual.
  - **After 14 days:** a deletion job removes every row for the account, with no anonymized copy and no audit
    trail kept: Portal (account, integrations, `integration_events`, Stations, sharing, assistant history, credits
    and the Agora Console connection), Auth (account, linked logins, clients, keys, audit rows) and Station
    (receipts, operational state, the archive of R9 log entries, the custom LLM key). Each Station receives a
    deletion request and confirms it; Portal retries until every Station has confirmed.
  - **Cancelling (owner decision):** during the 14 days, the person can sign in again and confirm "Restore my
    account". The account is re-enabled with its data. Revocations already made stay revoked: integrations need
    new keys and a new native approval, Stations are registered again, and shared access is granted again by the
    owners. After the 14 days, nothing can be restored.
  - **Backups (owner decision): kept at most 30 days**, so deleted data is gone from backups within 30 days of the
    final deletion. The deletion job also records the account ID in a deletion list that restores consult, so a
    restored backup can't bring the account back.

### 3.8 Discord

Discord runs on a Station that offers Station AI: a custom Station, or the built-in Station once it supports Station AI (D21 revised). Two ways to connect it:

**The official Agora.Build Discord app** (the default; one app for every custom Station, which are registered with
Agora.Build, §3.3):

- Agora.Build owns the install, consent, guild/channel/actor policy and the bot credentials. **The bot secret never
  leaves Agora.Build**; no Station operator receives it.
- Discord sends interactions to Agora.Build's interactions endpoint. Agora.Build verifies Discord's signature,
  deduplicates by interaction ID, finds the integration from the guild/channel, and forwards the interaction to that
  integration's Station; Station runs it through its agent module and returns the reply, which Agora.Build posts.
  Agora.Build keeps nothing beyond what's needed to deliver it (no stored transcripts).
- Installing the bot authorizes nobody by itself: each invocation must match an approved integration and an
  allowed Discord actor and channel (shared design, lines 455–466).

**Bring your own Discord app** (owner decision: supported, D22). For people who want Discord traffic to skip
Agora.Build entirely:

- The person creates their own Discord application and bot, and sets its **Interactions Endpoint URL** to their
  Station. Discord then talks to the Station directly; Agora.Build is not in the path.
- The bot token and the app's public key are entered in Astation's Station AI tab (Agent) and sent straight to the
  Station, stored there encrypted, like the custom LLM key; they never go to Agora.Build.
- Portal still manages the integration itself (name, allowed guild/channel/actors, expiry, revocation) and shows
  "Own Discord app" as its connection type; Station verifies Discord's signature with the app's public key and
  applies the same actor/channel checks.
- Delivered after the official app (later phase).

### 3.9 The assistant: voice pipeline on Agora.Build, intelligence on Station

```
Voice / text UI (Stoa, Astation)
        | audio / text
        v
Agora.Build voice agent: ConvoAI pipeline (ASR -> LLM call -> TTS)
        | OpenAI-compatible  POST /v1/chat/completions  (HTTPS, session token)
        v
Station LLM endpoint: context retrieval (RAG), function calling, the configured model
        | tool calls over R9 (end-to-end encrypted), through the Station relay
        v
Atem -> coding agents
```

- **Agora.Build hosts the assistant experience** as one ConvoAI pipeline, reusing Stoa's voice, the marketplace
  models and credits. **Conversation history is kept on Agora.Build** (transcripts and replies), visible and
  deletable by the person: **90 days on the free plan, forever on a paid plan** (§3.6).
- **Station hosts the "LLM"**: an OpenAI-compatible `/v1/chat/completions` endpoint with context retrieval, the
  context store and function calling inside. ConvoAI sees a plain chat model and declares **no tools**, so
  retrieved context and tool results stay on Station unless the reply contains them.
- **The assistant is an integration** (§3.1, §3.6): created on the Integrations page with explicit opt-in and
  scoped by its credential, Station's policy and the R9 grant.
- **Tokens (owner decision).** The agent is started once and never leaves or rejoins; ConvoAI's update call
  changes the running agent in place (same `agentId`, UID and channel; status stays `RUNNING`)
  ([update](https://docs.agora.io/en/api-reference/api-ref/conversational-ai/update)).
  - **LLM base URL and `api_key`: fixed for the whole conversation.** The `api_key` is a session token Auth issues
    when Agora.Build starts the voice agent: `aud` the Station, scope `assistant.chat` for that one assistant
    integration, `sid` = the assistant session ID, valid for the conversation (at most ConvoAI's 72-hour agent
    maximum). Station checks on every call that the `sid` is still active, so ending the session revokes it at
    once (Portal pushes the session end, Station polls). It can't reach any other Station API, integration or
    Station, and the integration's quota applies.
  - **Only the RTC/RTM token changes:** 30 minutes, refreshed in place every **20 minutes**, or at once on
    `104 agent expire`, with ConvoAI's update call (`properties.token`).
- **What leaves the person's machines:** audio, transcripts, replies and TTS text go through Agora's ConvoAI
  pipeline and are kept in Agora.Build's conversation history; each turn's `messages` array reaches Agora.Build
  and Station; Station's model call sends retrieved context to the configured provider (none, with a local model).
- **Reachability.** ConvoAI runs in Agora's cloud, so Station's LLM endpoint must be reachable over HTTPS. For a
  self-hosted Station behind NAT, the person exposes it themselves for now (cloudflared or ngrok); R9 and storage
  can stay private.

**Transport.** Atem opens an **outbound** WebSocket to its Station relay (`astation_relay_url`, default
`https://station.agora.build`, or the person's registered Station). Remote Astation, browser companions and
Station's agent module connect to the same relay, which routes by `atem_id` and `connection_id`. R9 is end-to-end
encrypted between each client and Atem, so the relay forwards ciphertext and sees only routing metadata, sizes and
timing; the agent module is itself an R9 endpoint and reads what its integration permits. The assistant always
reaches Atem through the Station relay (in-process when Station and Atem share a machine).

### 3.10 Astation settings tab: "Station AI"

A new tab in Astation's Settings, **Station AI**, with three switches, all off by default:

| Switch | What it enables on the account's Station |
|---|---|
| **MCP** | Station exposes an **MCP server** that outside AI clients (Claude Desktop, Cursor, other agents) can call, offering the same typed agent tools: list sessions, read status and history, send prompts, answer permitted approvals |
| **LLM** | Station's OpenAI-compatible `/v1/chat/completions` with context retrieval and function calling; the assistant (§3.9) calls it |
| **Agent** | Station's agent module and its integrations: Discord, custom apps, the assistant |

**No local transport while any switch is on.** "Relay only" means: Astation and Atem **do not use the direct local
WebSocket (`ws://*:8080/ws`)**; they connect through **the account's own Station relay**: `station.agora.build`,
or, for an account whose relay is a registered custom Station, **that Station's relay** (owner-confirmed; never a
fallback to `station.agora.build`). Everything else stays as it is today: `cred unlock` and credential sync keep working
the same way. The policy reaches Atem **the same way the relay configuration does with `station.agora.build`**, so
a custom Station needs no special mechanism. When all three switches are off, the direct transport may be used
again.

- **Where Station AI runs (owner decision, revised 2026-10-30).** Station AI runs on a Station that supports it: any
  registered custom Station that offers it, and the built-in `station.agora.build` once Agora.Build supports it there.
  Until a Station supports it, turning on a switch for an account whose relay is that Station is refused, and the
  Station rejects MCP, LLM and agent requests with: "Station AI is not available on this Station yet. Use a Station
  that offers it (Portal: Stations > Add Station) and select it in Astation." **Trust consequence:** Station AI decrypts
  the account's agent content on the Station that runs it. On a custom Station that is the owner's own server; on the
  built-in Station it means Agora.Build's server processes that content for the accounts that turn Station AI on there.
  Astation must say so when a person turns Station AI on with the built-in Station as their relay. The voice assistant
  (§3.9) and Discord (§3.8) need a Station that offers Station AI.
- **How it works: exactly like reaching Astation through `station.agora.build` today (owner decision).** Atem's
  connect loop (`src/app.rs`) tries the **local** link first (`astation_ws`, default `ws://127.0.0.1:8080/ws`), and
  if that fails connects to the **relay** (`astation_relay_url`: `station.agora.build` or the custom relay), joining
  the paired Astation's identity room by the `astation_id` in its pairing record; Astation is in the same room, and
  both dial out. With Station AI on, Atem **skips the local step** and always uses the relay, as an Atem on a remote
  machine already does. No R9 change:
  - Astation sends each of the account's Atem hosts **"relay only"** in a field of a message it already sends on
    the link; Atem saves it in its config, the same way it already learns and saves the relay identity.
  - Atem's connect loop: when "relay only" is set, don't try `astation_ws`; connect straight to the relay room.
  - Astation also refuses Atem connections on its local `:8080` listener while a switch is on, so a host that
    hasn't received the setting yet ends up on the relay and receives it there.
  - Switching on while Atem is connected locally: Astation sends the setting, closes the local link, and Atem
    reconnects through the relay. Switching off: Astation sends "relay only = off" and Atem tries local first again.
  - Everything on the link, including `cred unlock` and credential sync, keeps working, over the relay.
- **Scope:** the switches apply to the **whole account** (every Atem host and Astation device).
- The tab shows a banner while the policy is on: "Station AI is on: Astation and Atem connect through <Station>,
  not the local connection."
- The tab shows the account's Station and each feature's status (Off, Starting, On, Error). Turning a switch on
  shows what it does, which Station receives data and, for LLM, which model provider.

**LLM settings** (when LLM is on):

| Field | Notes |
|---|---|
| Provider | Station default, or **Custom (OpenAI-compatible)** |
| Base URL | e.g. `https://api.openai.com/v1`, a self-hosted vLLM or Ollama URL; https except for a Station-local address |
| Model | Free text (e.g. `gpt-4.1`, `qwen2.5-coder`) |
| API key | Write-only: entered once, never shown again (only "set, ending in …abcd"); Replace and Remove |
| Test | A minimal request through Station; shows success or the provider's error, never the key |

The custom key is **one key for the whole account**: set from any of the account's Astation devices, it goes
straight to the account's Station over its authenticated API, is stored there encrypted, and is used for all of the
account's devices. It never goes to Agora.Build, context or logs, and Astation keeps no copy after saving. The
consent text says the Station (and its operator) can use it and that prompts with retrieved context go to that
provider.
